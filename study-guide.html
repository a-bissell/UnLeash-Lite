SDP RCE Study Guide

WISCON 2026 // June 11, Madison WI

The Attack Chain

The one-sentence pitch: A heap overflow in the AWS KVS WebRTC SDK's SDP parser lets us inject a forged DTLS fingerprint via unauthenticated DDS multicast, establishing a data channel to upload and execute arbitrary code as root on the Unitree Go2.

ICE Gathering (local)

Create an aiortc RTCPeerConnection with iceServers=[] and generate a local SDP offer. Extract the DTLS fingerprint hash, ICE ufrag, ICE pwd, and host candidates from the local description.

On the isolated robot LAN there's no route to Google's STUN servers. Without iceServers=[], aiortc spends ~15 seconds retrying STUN before falling back to host candidates. The DDS exchange and DTLS handshake need to complete before the PeerConnection times out, so those 15 seconds are fatal. Setting iceServers=[] makes ICE gathering finish in under 1 second with host candidates only.
Build the Overflow SDP

Construct a crafted SDP with 5 media descriptions. The structure is precise:

  • MD0 m=fingerprint -- injection target. Our DTLS fingerprint hash sits in the i= (session information) line at byte offset 8.
  • MD1-3 m=video -- minimal padding to reach the right struct layout.
  • MD4 m=application -- the real data channel description, carrying ICE credentials, host candidates, and 256 attributes (255 padding + 1 overflow).
The 256th attribute in MD4 has a 522-byte name: 520 bytes of 'A' followed by \x01\x01. The value is just "overflow".

When parseMediaAttributes() processes this attribute, bytes 520-521 of the name land on the sessionAttributesCount field in the SDK's session descriptor struct. This is a UINT16 in little-endian, so \x01\x01 = 0x0101 = 257.

The session-level attribute loop now iterates up to index 256. Index 255 is the last legitimate slot. Index 256 reads past the array boundary into adjacent memory, which maps to MD0's mediaName and mediaTitle fields.

mediaName = "fingerprint" (from m=fingerprint), and mediaTitle[8] onward contains our SHA-256 hash (from i=sha-256 XX:XX:...). The SDK sees attributeName="fingerprint" and writes the value into the PeerConnection's expected fingerprint field at PC+0xc4255.
DDS Multicast Exchange

Publish the overflow SDP as a JSON payload to rt/webrtcreq via CycloneDDS. The robot's webrtc_bridge picks it up, parses the SDP (triggering the overflow), and publishes its answer to rt/webrtcres. Poll the response topic for up to 15 seconds.

The robot runs CycloneDDS 0.10.2. Version 0.11+ changed the SEDP (Simple Endpoint Discovery Protocol) wire format. If the versions don't match, the DDS participants can't discover each other's topics and no messages are exchanged. The version must be an exact match at 0.10.x.

This also means cyclonedds 0.10.2 must be built against the system's CycloneDDS C library at the same version, and it won't compile on Python 3.14+ due to removed CPython internals (_Py_IsFinalizing()).
The overflow SDP contains raw \x01 bytes (the two-byte suffix on the overflow attribute name). Python's json.dumps() escapes these to , which is a valid JSON escape but the robot's parser handles it differently than the raw byte. Building the JSON string manually preserves the raw bytes in the SDP, which is required for the overflow to land correctly on sessionAttributesCount.
Answer Rewriting

The robot's answer SDP contains 2 media sections: m=video (mid:0) and m=application (mid:1). Our local description has 1 media section: m=application (mid:0). Strip the video section and renumber mid:1 to mid:0 so aiortc can accept it.

DTLS Handshake + Data Channel

Set the rewritten answer as the remote description. aiortc performs ICE connectivity checks (host candidates only, sub-second), then the DTLS handshake. Because the overflow injected our fingerprint into the robot's expected fingerprint field, the robot accepts our certificate. SCTP negotiation follows and the data channel opens.

The Go2's WebRTC bridge never completes the DCEP (Data Channel Establishment Protocol) handshake. aiortc's data channel stays in a non-open state. The code force-sets dc._setReadyState("open") in the message handler when the first message arrives. Without this, dc.send() would throw.
Validation + Upload (race against session close)

The robot sends a validation challenge. Respond with base64(md5("UnitreeGo2_" + challenge)). On "Validation Ok.", immediately fire the payload upload to rt/api/programming_actuator/request with api_id=1002.

Everything from subscribe to upload fires inside the @dc.on("message") handler because the SDK detects corrupted internal state and closes the session ~1-2 seconds after DTLS completes.

The heap overflow corrupts SDK state beyond just sessionAttributesCount. The SDK detects inconsistent internal state shortly after the DTLS handshake and transitions to RTC_PEER_CONNECTION_STATE_CLOSED. Critically, the process does not crash -- it continues running and can accept new connections. This means:

1. The subscribe, validation, and upload must all happen in the message handler callbacks (synchronous with message receipt), not in a sequential async flow.

2. There's no time for a list_programs confirmation (api_id 1001) after the upload. The upload is fire-and-hope.

3. The @dc.on("close") and @pc.on("connectionstatechange") handlers serve as fallback signals. If the connection dies after the upload was sent but before a response arrives, the result is "sent but unconfirmed" -- the tool proceeds to the trigger step anyway.
Fake Controller Trigger via DDS

Create a new DDS participant and publish a WirelessController_ message to rt/wirelesscontroller with keys=2050 (L1+Y). Hold for 300ms, then send keys=0 (release). The programming_actuator service reads this topic and executes the bound script as root.

From physical_remote_controller.py on the robot: 
R1  = 1       (0x0001)
L1  = 2       (0x0002)
L2  = 32      (0x0020)
A   = 256     (0x0100)
B   = 512     (0x0200)
Y   = 2048    (0x0800)

L1+Y = 2 + 2048 = 2050
L2+Y = 32 + 2048 = 2080
R1+Y = 1 + 2048 = 2049
The programming_actuator checks self.value == (button_combo) exactly, so the keys field must match the sum precisely. The WirelessController_ IDL type is: {lx: float32, ly: float32, rx: float32, ry: float32, keys: uint16}.
Payload Execution

For bypass-ssh: the payload writes a cron job to /etc/cron.d/ush that sets the root password, enables SSH, starts sshd, and self-deletes. Cron fires within 60 seconds. The payload passes the keyword blocklist because all strings are encoded as str(bytes([...]), 'utf-8') and file I/O uses np.savetxt instead of open()/write().

Firmware 1.1.14+ (programming_actuator 1.0.5.5) scans uploaded Python source for ~180 blocked keywords before execution. The list includes import, open, write, exec, os.system, subprocess, socket, /bin, bash, and many more.

The bypass encodes every sensitive string as a runtime-constructed byte array: 
"/etc/cron.d/ush"  -->  str(bytes([47,101,116,99,...]), 'utf-8')
The tokens str, bytes, and 'utf-8' are not in the blocklist. np (NumPy) is pre-imported in the execution sandbox, and np.savetxt is not blocked. The seccomp filter whitelists openat, write, and close syscalls (NumPy needs them), so np.savetxt can write files.

The cron job itself runs outside the seccomp sandbox -- crond is a separate process with no restrictions. This is how bypass-ssh escalates from "can write files" to "can run arbitrary shell commands."

Deep Dives

The Vulnerable Function: parseMediaAttributes() expand

parseMediaAttributes() in the AWS KVS WebRTC C SDK parses SDP attribute lines (a=key:value) within each media description. It stores them in a fixed-size array on the session descriptor struct.

The bug: no bounds check on the attribute count. The array has room for 256 entries (indices 0-255). If a media description contains more than 256 attributes, writes go past the end of the array into adjacent struct fields.

At index 256, the write lands on sessionAttributesCount (a UINT16). The attribute name bytes at offset 520-521 overwrite this field. The attribute value is irrelevant to the overflow itself.

AWS patched this in KVS WebRTC SDK v1.18.1 by adding a bounds check. The Unitree Go2 ships with an older SDK version and has not updated.

SDP Structure: Why 5 Media Descriptions? expand

The overflow at index 256 reads from memory that corresponds to MD0's parsed fields in the session descriptor's media description array. We need MD0 to contain our fingerprint data, so it must exist.

MD0 (m=fingerprint): Not a real media type. The SDK parses the m= line and stores "fingerprint" as mediaName. The i=sha-256 HASH line goes into mediaTitle. When the overflowed loop reads index 256, it sees attributeName="fingerprint" and treats the value (from mediaTitle at offset 8) as a session-level fingerprint.

MD1-3 (m=video): Padding. The struct layout requires these to push MD4 to the right position. They carry ICE credentials but no candidates or payload.

MD4 (m=application): The actual data channel description with ICE candidates. This is where the 255 padding attributes and the 1 overflow attribute live.

DDS Multicast: Unauthenticated by Design expand

The Go2 runs CycloneDDS on domain 0 for inter-process communication. The webrtc_bridge service subscribes to rt/webrtcreq and publishes answers to rt/webrtcres. These topics use standard DDS multicast with no authentication, no encryption, and no access control.

Any device on the same LAN that joins DDS domain 0 can publish to these topics. The bridge accepts whatever it reads and passes the SDP directly to the KVS SDK parser. There is no validation of the offer's origin, structure, or content before parsing.

This is why the SDP overflow is pre-auth: it reaches the vulnerable parser through a channel that has no authentication layer at all. The HTTP signaling path (port 9991) at least requires an AES key exchange on firmware >= 1.1.15, but the DDS path has nothing.

DTLS Fingerprint Injection Mechanics expand

Normal WebRTC: the SDP offer contains a=fingerprint:sha-256 HASH at the session level. The answerer stores this hash and later verifies that the offerer's DTLS certificate matches it during the handshake.

The overflow corrupts sessionAttributesCount to 257, causing the attribute loop to read one extra entry. That entry's data comes from MD0, where mediaName="fingerprint" and the value is our controlled SHA-256 hash from the i= line.

The SDK processes this as if it were a legitimate session-level fingerprint attribute, overwriting the previously stored (legitimate) fingerprint at PC+0xc4255 with our value. The session-level a=fingerprint: line still contains a valid-looking hash (a hardcoded safe value), but it gets overwritten by the injected one.

When DTLS begins, the robot checks our certificate against the injected hash, which matches our actual certificate. Handshake succeeds.

The Session Close Constraint expand

The heap overflow doesn't just corrupt sessionAttributesCount. The 520 bytes of 'A' and the broader attribute array overflow corrupt other fields in the session descriptor. The SDK detects this inconsistent state roughly 1-2 seconds after the DTLS handshake and transitions to RTC_PEER_CONNECTION_STATE_CLOSED. The process does not crash -- it continues running and accepting new connections.

This creates a hard timing constraint: everything must happen within that 1-2 second window. The tool handles this by doing all work in the @dc.on("message") callback:

1. First message arrives -> force data channel open, subscribe to programming_actuator response topic
2. Validation challenge arrives -> send response
3. "Validation Ok." arrives -> immediately fire the upload
4. If upload response arrives before close -> confirmed success
5. If session closes first -> "sent but unconfirmed," proceed to trigger anyway

This is why the SDP path can't do a list_programs check after upload (the HTTP signaling path can, because its connection is stable).

Firmware 1.1.14 Defenses and How They're Bypassed expand

Firmware 1.1.14 added three defenses to programming_actuator:

1. Keyword blocklist (~180 keywords): Scans Python source before execution. Blocks import, open, exec, os.system, subprocess, socket, /bin, bash, etc. Bypassed by encoding all strings as str(bytes([int,...]), 'utf-8') and using np.savetxt for file I/O. Neither str, bytes, np, nor savetxt are in the blocklist.

2. seccomp sandbox (py_script_execute_env): Restricts syscalls available to the Python process. But it whitelists openat, write, and close (because NumPy needs them), so np.savetxt can write files. The escape: write a cron job file to /etc/cron.d/. When crond (running outside the sandbox) picks it up, commands execute unrestricted.

3. UUID validation: program_uuid must be exactly 10 digits. The tool uses str(int(time.time())) which produces a 10-digit Unix timestamp.

Firmware 1.1.15 added per-device AES-128 authentication to the HTTP signaling path, but the DDS path remains unauthenticated.

programming_actuator: The Root Code Execution Service expand

programming_actuator is a Python service on the Go2 that provides a "visual programming" feature through the Unitree app. It accepts Python scripts over the internal DDS bus, writes them to /unitree/etc/programming/<uuid>.py, and binds them to controller hotkeys. When the hotkey is pressed, the script runs as root.

It exposes two DDS API endpoints via rt/api/programming_actuator/request:

api_id 1001: List registered hotkey programs
api_id 1002: Upload a new program (chunk_content + program_uuid + bind_hotkey)

The service also subscribes to rt/wirelesscontroller to detect button presses. This is how the fake controller trigger works -- publish a matching WirelessController_ message and the service fires the bound script.

This service is the same one exploited by Boschko's direct DDS attack (CVE-2026-27509). The difference is the delivery path: Boschko joins DDS domain 0 and sends directly to programming_actuator. UnLeash Lite delivers payloads through the WebRTC data channel, which bridges to the same internal DDS bus.
